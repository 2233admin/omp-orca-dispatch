# Design: Parent coordination layer (ledger + collect + integrate)

## Problem Statement

`orca_task_dispatch` plans and creates children, then stops. Everything after
dispatch is manual. Measured on three real dispatch rounds in one session:

- Integration was done by hand three times: open each child worktree, inspect
  the diff for scope violations, run the gates, decide whether it can merge.
- Polling was hand-written each round. Round one used the wrong base commit,
  so a worker that had already committed was misread as stuck.
- Nothing records what was dispatched. "What did I send out, and who has not
  come back" lives only in the operator's head.

Doing nothing means every dispatch round needs the operator present to babysit
it, which defeats the fire-and-forget workflow the tool exists to serve.

## What Makes This Cool

One command turns N child worktrees into a single screen the operator can act
on, and merges the ones that are unambiguously safe without asking. The
operator only sees the cases that genuinely need a human call.

The novel part is not automation, it is the split: machine-checkable
conditions merge themselves; anything requiring a value judgment stops and is
reported. Multi-agent tools generally have neither an auditable execution
ledger nor an explicit boundary between those two classes.

## Constraints

- The package holds no credential and never executes a tracker command.
- Nothing lands in the parent checkout without passing the gate policy.
- argv only, no shell strings.
- No new runtime dependency.
- Output is one terminal screen aimed at the operator, not a machine-readable
  feed and not a PR comment.

## Premises

1. The pain is real, not hypothetical. Evidence: three hand integrations and
   three hand-written polling loops in one session, plus one false "worker
   stuck" verdict caused by an unrecorded base commit.
2. Reuse the journal primitives, not the backlog log. `offline.ts` already
   proves the pattern: append-only JSONL, last-record-wins `replay`,
   `withLock`, idempotent transitions, host-ownership checks. The ledger gets
   its own file, its own schema, and its own replay.
   Corrected during the session: `offline.ts` `replay()` accepts only
   `enqueue`/`claim`/`bind`/`complete`/`ack` and **throws** on a
   schema-invalid record rather than skipping it, because silently dropping a
   record could hide an acked item and cause a duplicate tracker write.
   Writing dispatch events into that same log would corrupt the backlog.
3. The ledger must record `baseHead`. `ParentContext.head` is already the
   exact committed HEAD; the session's false "stuck" verdict happened only
   because nothing persisted it.
4. Revised by the user during the session: `integrate` **does** merge
   automatically when every machine-checkable condition passes. Any condition
   requiring a value judgment holds and reports instead of guessing.
5. Per-child green does not imply the batch is green. An independent cold read
   (codex) and the session's own practice agree: ownership measures scope, not
   compatibility, so two children can touch disjoint paths, pass individually,
   and still break a shared contract together. All three hand integrations
   this session ran the full gate **after** merging, never before.
   Therefore auto-merge is only defensible when the combined tree is gated.
6. Verification must be bound to immutable SHAs, and the gate definition must
   come from parent-side policy. A child may not define or weaken its own
   acceptance checks; that is exactly why Approach C was rejected.
7. A git merge and a ledger append cannot commit atomically. Idempotent
   transitions do not cover a crash between them, so recovery reconciles
   recorded commit identities against actual git ancestry before retrying.
8. All-or-nothing needs an immutable round, not just per-child state. A
   per-child state machine cannot tell whether an integration request covers
   every child dispatched together, so the ledger records a `round` with a
   generated id and its complete child set at dispatch time. Every child
   event carries that id, and `integrate` takes a round id, never a
   caller-assembled list of children.
9. Only the parent writes the ledger. `offline.ts` derives its state filename
   from `repositoryKey(cwd)`, which resolves each worktree's own root, so a
   parent and its children would never address one log. Rather than hand a
   child a shared ledger handle, the parent resolves each child's branch head
   itself when it needs it. A child writes code and commits; it never writes
   coordination state and is never told the ledger path. This is a protocol
   boundary, not a sandbox: a worker running as the same user can still reach
   the filesystem, so the guarantee is that no child is *asked* to report
   state the parent then trusts, which is the trust problem that sank
   Approach C.

## Approaches Considered

### Approach A: collect only, smallest diff
Write a `dispatched` event into the existing backlog JSONL and have one
`collect` command read it, run gates, and merge when green. Rejected: writing
a foreign `kind` into that log makes `replay()` throw and corrupts the
backlog, and it fuses "look" with "merge" in one command.

### Approach B: ledger + collect + integrate (chosen)
New `src/ledger.ts` reusing the journal primitives with its own store and a
round-level state machine `round → attempt → merged | held`. `collect`
inspects and reports without touching git state or the ledger. `integrate`
snapshots, gates, and merges under a parent-owned policy.

### Approach C: signed worker receipts, parent verifies only
Each child runs its own gates and writes a receipt; the parent checks the
receipt instead of re-running gates. Rejected on the trust boundary, not on
observed worker misbehaviour: all six workers this session passed their gates
honestly. The objection is structural. A receipt lets the party being verified
define its own acceptance, so the parent can no longer distinguish "gates
passed" from "gates were declared passed", and a receipt says nothing about
the combined tree. The parent must independently gate pinned SHAs under its
own policy.

## Cross-Model Perspective

Independent cold read by codex-cli 0.153.4, given only this document and no
access to the session that produced it.

- Steelman: B fixes the actual operational failures with a durable dispatch
  record, a persisted base commit, and parent-run verification. A separate
  ledger avoids breaking backlog replay, and splitting inspection from
  integration gives visibility without moving branches.
- Premise challenged: "passing gates and staying inside owned paths" does not
  establish safety. Ownership measures scope, not compatibility. The document
  treated the limits of its own checks as the boundary of risk.
- Missed pitfall: a git merge and a ledger append cannot commit atomically. A
  crash between them leaves a merged child recorded as unmerged, and
  idempotent transitions do not cover it.
- Verdict on auto-merge as originally written: not safe. It required pinned
  SHAs, serialized integration, candidate verification in an isolated
  worktree, an atomic parent update that rejects a changed HEAD, and gate
  definitions owned by the parent rather than the child.

All four points were accepted and folded into the premises, success criteria,
and next steps above.

## Recommended Approach

Approach B. Safe auto-merge requires that "machine-checkable" and "needs a
human" be two separately invokable stages rather than one fused command. It
also keeps `collect` side-effect free, so the operator can inspect before
anything moves.

## Success Criteria

- Dispatch writes a `round` record with a generated round id and its complete
  child set. Per child it records only what exists at dispatch time: slice,
  owned paths, `baseHead`, worktree identity, and branch. A child head SHA
  cannot exist yet and is never recorded here.
- `collect` is pure inspection. It reads the ledger and git, prints one
  screen, and appends nothing. It never resolves the gate policy and never
  runs a gate. It answers "what is outstanding" without a hand-written loop.
- There is no `committed` state and no observe command. "Has this child
  committed yet" is derived from git at read time, never stored, so no command
  needs to append a record before `integrate` may run and a fresh round can
  never deadlock.
- `integrate` owns all verification. It takes a **round id**, never a
  caller-assembled child list. It snapshots every recorded member's branch
  SHA in one pass and writes them into a single `attempt` record. It rejects
  the round if any member is unresolvable, or still resolves to `baseHead`,
  meaning that child has not committed. Those snapshot SHAs are what it
  verifies and merges; it trusts no earlier record.
- `integrate` builds a temporary integration branch from the recorded
  `baseHead` in an isolated worktree, merges the whole round there, and runs
  the full gate **once on the combined tree**. Only an all-green combined tree
  fast-forwards the target.
- The gate policy lives at `.orca-task-dispatch/gates.json` in the parent
  checkout, carries a `schemaVersion`, and is digested over a canonical
  serialization recorded with each attempt. Missing, unparseable,
  schema-invalid, unsupported-version, and out-of-bounds values all produce
  one outcome: the round is `held` with the reason recorded, and neither a
  candidate nor the target is created or mutated.
- The target advances by a guarded, serialized fast-forward, not an atomic
  primitive. Under the ledger lock, in the recorded parent worktree: require
  the tree clean, re-read the target SHA, require it to still equal the
  snapshotted value, then run `git merge --ff-only <candidateSHA>`. Direct
  `update-ref` is not used because it would desynchronize a checked-out
  worktree from its index. The merge and the ledger append are not atomic
  together, so crashes are reconciled by ancestry rather than assumed away.
- There is exactly one gate run, on the combined tree in the isolated
  integration worktree. Scope is enforced separately and earlier, by diffing
  each member's `baseHead..memberSha` against its recorded owned paths before
  anything is created. A scope violation, a combined-tree gate failure, or a
  cross-child conflict ends the whole round as `held` with the reason on
  screen. The target is either fully advanced or unchanged.
- `held` is terminal for that round. Recovery is a **new** round that
  supersedes it, carrying the repaired children's new SHAs and referencing the
  superseded round id. A held round is never revived in place, so a pinned SHA
  is never reinterpreted.
- Only the parent appends ledger records. No child receives a ledger path or
  writes coordination state.
- After a crash mid-integration, a rerun reconciles the ledger against git
  ancestry and neither double-merges nor reports a merged child as outstanding.
- Ledger replay tolerates exactly one malformed final record with no later
  nonblank record, which is the interrupted-append case that crash recovery
  depends on. A schema-invalid record anywhere, and a malformed record that is
  not final, fail loudly. This matches `offline.ts` `replay()` behaviour
  rather than the stricter rule an earlier draft of this document claimed.
- The round-one failure is unreproducible: an already-committed child is never
  reported as outstanding.

## Next Steps

1. Ledger locator. The new ledger does **not** reuse `offline.ts`'s private
   `stateFile()` keying, which hashes the worktree root and therefore differs
   per worktree. `src/ledger.ts` computes
   `key = sha256(JSON.stringify([backend.id, context.repoId, context.worktreeId]))`.
   Note the sources: `backend.id` comes from `WorktreeBackend.id`; only
   `repoId` and `worktreeId` come from `ParentContext`, which today carries
   exactly `repoId`, `worktreeId`, and `head`. No `backendId` field is added
   to `ParentContext`. The ledger layer names the third input
   `parentWorktreeId` for readability. The ids are used as supplied, with path
   separators normalized to `/` and one trailing slash stripped; they are
   **not** lowercased, because on a case-sensitive filesystem two distinct
   parents can differ only by case. The log is
   `~/.orca-task-dispatch/ledger/<key>.jsonl` and its lock is the sibling
   `<key>.lock`, both outside every worktree. The backend contract gains one
   guarantee, for the two context identities only: `repoId` and `worktreeId`
   are stable across invocations for the same parent. Because the key includes
   the parent worktree, `collect` and `integrate` must run from the same
   parent that dispatched the round; invoked elsewhere they resolve a
   different, and therefore empty, ledger. That is a stated precondition.
2. `src/ledger.ts`: own record schema, own `replay`, reusing the append-only
   + `withLock` + idempotency pattern. Records, each carrying `roundId`:
   - `round`: the requested member set (slice ids and owned paths),
     `baseHead`, optional `supersedes`. Written **before** any child is
     created, so membership is immutable and cannot shrink to whatever
     happened to succeed.
   - `dispatched`: one per successfully created child, adding its worktree
     identity and branch.
   - `dispatch-failed`: terminal, naming the members that could not be
     created.
   - `attempt`: the resolved gate-policy digest, every observed member SHA,
     the snapshotted target SHA, and the gated candidate SHA.
   - `merged` or `held` (with reason): the round outcome.
   No `committed` and no `verified` record exists. Replay tolerates only a
   malformed final record.
3. Dispatch is a ledger transaction. Append `round` with the full requested
   member set first, then create children, then append one `dispatched` per
   success. If any creation fails, append `dispatch-failed` and the round is
   terminal `held`; recovery is a superseding round. `integrate` requires one
   `dispatched` record for every requested member, so an incomplete set can
   never be mistaken for the round. Crash recovery reconciles by looking for
   a child worktree matching a requested member that has no `dispatched`
   record: that member is treated as not created, and the round is `held`.
   Children never touch the ledger and never receive its path.
4. Gate policy at `.orca-task-dispatch/gates.json` in the parent checkout:
   `{"schemaVersion": 1, "gates": [{"name": string, "argv": string[],
   "env": "inherit" | "none", "timeoutMs": integer 1000..1800000}]}`. There is
   no `cwd` field: every gate runs in the isolated integration worktree, which
   is the only tree that represents the combined result. A gate that ran in
   the parent checkout would test the unchanged target and prove nothing.
   `argv` must be non-empty and is never a shell string. The digest is
   `sha256` over `JSON.stringify` with object keys sorted and no insignificant
   whitespace. Missing, unparseable, schema-invalid, unsupported
   `schemaVersion`, and any out-of-bounds `timeoutMs` resolve to one outcome:
   `held`, reason recorded, nothing mutated. A gate that exceeds its timeout
   is a gate failure.
5. `collect`: pure inspection, by round. Per child, commits since `baseHead`,
   diff paths versus owned paths, cross-child path overlap, and whether the
   branch has moved off `baseHead` at all. It reports; it never enforces.
   Appends nothing, resolves no policy, runs no gate. One screen.
6. `integrate <roundId>` in this exact order:
   a. Require one `dispatched` record for every requested member, else `held`.
   b. Snapshot the target branch SHA and every member's branch SHA in one
      pass. Reject if any member is unresolvable or still at `baseHead`.
   c. Resolve and validate the gate policy, computing its digest. Any policy
      failure is `held` here, before anything is written or created.
   d. **Scope enforcement, pre-merge:** for each member, diff
      `baseHead..memberSha` and reject the round if any changed path falls
      outside that member's recorded owned paths. This is where a scope
      violation is caught. `collect` only reports; `integrate` enforces.
   e. Create a fresh isolated integration worktree at the snapshotted target
      SHA, not at `baseHead`, so a target that legitimately advanced since
      dispatch can still be advanced; `baseHead` is used only to compute each
      member's own commit range and diff. Merge the whole round there.
   f. Run the gates once on the combined tree, in that worktree.
   g. Append `attempt` carrying the policy digest, every member SHA, the
      snapshotted target SHA, and the gated candidate SHA. This record is
      durable **before** the target is touched, which is what makes crash
      recovery decidable.
   h. Update the target, then append `merged`.
   Any failure appends `held` with the reason and leaves the target untouched.
7. Target update is a guarded, serialized fast-forward. Under the ledger lock,
   in the recorded parent worktree: require the tree clean, re-read the target
   SHA, require it to still equal the snapshotted value, require the candidate
   to be a descendant, then run `git merge --ff-only <candidateSHA>`. Never
   `update-ref`, which would leave a checked-out worktree out of sync with its
   index. A changed target, a dirty tree, or a non-descendant candidate abort
   with the target untouched and the round `held`, so the operator reruns
   against the new target.
8. Recovery path: reconcile the ledger against git ancestry on startup. An
   `attempt` with no outcome record is decided by testing its recorded
   candidate SHA against the target's ancestry: if the target contains that
   candidate, the merge landed and only the append was lost, so record
   `merged`; otherwise nothing landed and the round is `held`. The candidate
   SHA is available because step 6g persists it before any target move.
   A `held` round is terminal; recovery dispatches a superseding round.
9. Tests: `held` when a requested member has no `dispatched` record, `held` on
   `dispatch-failed`, rejection when a member is unresolvable or still at
   `baseHead`, `held` on a pre-merge scope violation with nothing created,
   `held` on combined-tree gate failure with the target unchanged, `held` on
   conflict, auto-merge on all-green, a target that advanced after dispatch
   still integrating cleanly, rejection when the target SHA changed between
   snapshot and compare-and-set, rejection on a dirty target, rejection when
   the candidate is not a descendant of the target, `held` for each
   gate-policy failure mode including a timeout and with no `attempt` written,
   `collect` appending nothing, `collect` from a different parent worktree
   resolving a different and empty ledger, replay tolerating a torn final
   record but failing on a schema-invalid or non-final malformed record,
   superseding a held round, crash recovery deciding `merged` by ancestry from
   the recorded candidate SHA, idempotent reruns, and the round-one regression
   where a child that has committed must not read as outstanding.

## Resolved During The Session

- Batch semantics: **all-or-nothing** per round. Any `held` child refuses the
  whole round; the target stays unchanged. Chosen because dispatch rounds this
  session were always paired slices (a code slice and its documentation
  slice), so landing half a round leaves code without its docs or docs
  describing code that is not there. It also keeps crash recovery simple: the
  target is either fully advanced or untouched.
- A `held` round is terminal and is recovered by a superseding round, not
  revived in place, so a pinned SHA is never reinterpreted.
- `collect` is pure inspection; `integrate` owns every gate run and every
  ledger append, and trusts no prior verification record.
- The ledger keys on normalized `repoId` + `worktreeId` under a state root
  outside every worktree, not on `offline.ts`'s per-worktree `stateFile()`.
- `integrate` uses a fresh integration worktree per run. Safety over speed;
  reuse would carry state between rounds.

## Reviewer Concerns

Three rounds of adversarial review ran, the maximum for this workflow. Scores
were 6, 5, then 4 out of 10. Each round raised **new** issues rather than
repeating the previous ones, so the falling score reflects deeper reading of a
document that kept growing more specific, not regression. Fifteen issues were
raised in total and all fifteen were fixed on disk. The round-three fixes were
applied **after** the third review and have therefore not themselves been
reviewed. Treat these as the places to look first:

- Scope enforcement had no executor. The success criteria demanded a hold on
  scope violations while the `integrate` flow only ran SHA checks, a merge,
  and the combined gate, so an out-of-scope edit could have landed whenever
  the combined gate passed. Now an explicit pre-merge diff check, step 6d.
- `attempt` was specified to carry the policy digest but was written before
  the policy was resolved. Ordering fixed; the policy now resolves first.
- Crash recovery tested a candidate SHA that no record stored. `attempt` now
  persists the candidate and target SHAs before any target move.
- Partial dispatch had no representation. The dispatcher creates children
  concurrently and can partly fail, so membership is now written before any
  child is created, and a failed creation is a terminal `dispatch-failed`.
- `cwd: "repoRoot"` in the gate policy would have gated the unchanged target.
  Removed; gates run only in the integration worktree.
- The document claimed `backendId` came from `ParentContext`. It does not:
  that type carries `repoId`, `worktreeId`, and `head`, and the backend id is
  `WorktreeBackend.id`. Corrected, with no new field added.

Two earlier corrections are worth remembering because both were this
document asserting something false about its own codebase: that writing
dispatch events into the backlog log was safe (it corrupts it), and that
`replay()` fails loudly on any malformed line (it deliberately tolerates a
torn final record, which is exactly what crash recovery needs).
